# The 3D pages

> ⚠️ **By Ihor Ivaniuk (@IBITLAB): idea, tasks, decisions; executed by AI (Claude Code).** Not checked by an engineer, never built, never tested. The full disclaimer is in [README.md](../README.md#disclaimer).

Two versions of one interactive page for the model `scad/excavator_boom.scad`: orbit the machine, move the boom, stick and bucket, rebuild it with any other parameter. The live one is published on GitHub Pages.

| Page | Start | Rebuild after a parameter change | What it needs |
|---|---|---|---|
| With a server | `web/viewer.sh` → `viewer.py` + `viewer/index.html` | ≈ 0.4 s (desktop OpenSCAD) | Python and OpenSCAD; Ukrainian only |
| No backend | `web/viewer-wasm.sh` → `viewer-wasm/` (Vite) | ≈ 2.2 s (OpenSCAD-WASM in the browser) | Node to build; two languages, phones, AR |

The rest of the technical detail is in [docs/TECHNICAL.md](../docs/TECHNICAL.md); how the pages get their data (the `VIEW` echo, the OFF meshes, the shared code blocks) is in [docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md) and [docs/GEOMETRY.md](../docs/GEOMETRY.md).

## 1. The page with a server (`web/viewer/`)

```
web/viewer.sh                                   # opens http://127.0.0.1:8765/ in the browser (Ctrl+C to stop)
python3 web/viewer.py --export file.html        # a static page with no server (one ships with every version: latest/viewer.html)
```

- **Mouse**: left button orbits, right button or Shift pans, the wheel zooms towards the cursor, a double click on a part sets a new orbit centre. There are view buttons (side, isometric, top, front, fit) and a perspective / orthographic toggle.
- **The boom, stick and bucket angles** move the model instantly: the page assembles the pose itself, using the same formulas as the model's `pt_*()` functions and the points the model prints in `echo(VIEW = …)` (cross-checked against the model's echo: the tooth position and the cylinder lengths agree to within 0.1 mm). The slider limits come from the cylinder strokes; next to each angle you see the cylinder length and the stroke used. Clear "limit to cylinder stroke" and a cylinder beyond its stroke turns red. Ready-made poses and a "dig cycle" are included.
- **Every other parameter** (the Customizer groups are read straight from the `.scad` — there is no separate list) goes to a local server: it runs OpenSCAD in parallel for 12 parts in their own coordinate frames and returns coloured meshes (OFF format). Changed parameters are highlighted; "Copy changes" gives you lines ready to paste into the `.scad`; "Reload model" picks up edits to the file. Warnings from the model (`!!!` — a dead centre in the linkage, an unreachable cylinder length) are shown on screen.
- The server listens on 127.0.0.1 only; values coming from the browser are coerced to the types in the schema (numbers, booleans, enumerations), so arbitrary text never reaches OpenSCAD. three.js is loaded from a CDN (jsdelivr) — an internet connection is required.

## 2. The page with no backend: OpenSCAD-WASM in the browser (`web/viewer-wasm/`)

```
cd web/viewer-wasm && npm install      # dependencies: three, openscad-wasm-prebuilt (OpenSCAD 2025.01 + Manifold, 11 MB), vite
npm run dev                              # http://localhost:8766/ — editing scad/excavator_boom.scad reloads the page at once
npm run build                            # a static site in dist/ (≈12 MB): drop it on any static host
npm run preview                          # view the built dist/ locally
npm test                                 # a smoke test with no browser
# the same in one command from the repository root: web/viewer-wasm.sh [build|preview|phone|test]
# phone — build and serve it to your phone on the same Wi-Fi (Vite otherwise listens on 127.0.0.1 only)
```

- The same page and the same controls as the server version (which is still there: `web/viewer.sh`), except that **OpenSCAD runs in a web worker in the browser**; neither Python nor an installed OpenSCAD is needed. The model is embedded into the page at build time (a `?raw` import) and the Customizer parameters are parsed by JavaScript (`src/schema.js`).
- One engine run per parameter change: in `part="view_all"` mode the model lays all 12 parts out with an offset along Y and the page cuts the mesh back apart (`src/offmesh.js`). Measured in Chrome: the first start takes ≈ 5 s (loading the engine), a **rebuild after a parameter change ≈ 2.2 s**; the angles remain instant. For comparison, the server version rebuilds in ≈ 0.4 s.
- **Two languages: English and Ukrainian.** A `UK | EN` switch sits in the panel header; the language comes from `?lang=en` in the URL, then from the browser's storage, then from the browser's own language. Switching only redraws the labels — OpenSCAD is not restarted, and the angles, checkboxes and changed parameters all stay as they were. The group names and the descriptions of all 103 model parameters are translated too: the English texts live in `src/i18n.js` while the Ukrainian ones are read straight from the `.scad` comments, so the model remains the single source of truth. `npm test` verifies that the dictionary has not drifted from the model (every group and every documented parameter has a translation) and that both languages carry the same keys. Warnings printed by the model itself (`!!!`) stay in Ukrainian — they come from `echo()` in the `.scad`. The server page (`web/viewer.sh`) is Ukrainian only.
- **The page reads only the language from the URL** (`?lang=en`). Initial parameter values used to be given there too — that was removed on purpose: it was the one path by which a value from someone else's link reached the text of the OpenSCAD model. The model is embedded into the page at build time, and **there is no way to open somebody else's `.scad` in it either** — that was removed on purpose: such a file's text would become the group names, descriptions and warnings in the panel, i.e. foreign data inside a page that lives on a shared GitHub Pages domain.
- **On phones and tablets the panel is a bottom drawer** with three states: collapsed (just the grab bar with the reach and the tooth height — the model gets 93 % of the screen), working (the three angle sliders and the ready-made poses) and full (the view presets and visibility checkboxes as well). Drag it by the handle, tap the handle to collapse or expand. The layout is triggered not only by width but by `pointer: coarse`: a phone held sideways (844 px) and a tablet in portrait (768 px) would otherwise get a side column taking half the screen. Model parameters, devices and the render views are hidden on touch devices — nobody edits those from a phone. The AI warning is collapsed by default **everywhere** — only the summary line shows and the reader opens the rest themselves; on a phone it sits behind a ⚠ icon on the handle, next to the collapse button and the language switch, and opens as a card over the model. The handle sticks to the top of the panel, so you can collapse and expand from anywhere in the scroll — and the scroll position is kept. A note at the bottom of the panel says what the phone version leaves out. On a phone the view presets sit as **icons in the "Angles" heading row** — an isometric cube with the face you are looking at shaded, the way CAD tools do it. The whole set then fits on the first screen without a block of its own; on a desktop the label stays next to the icon. The projection is a state rather than a view, so it sits in a group of its own behind a divider, is round instead of rectangular, and its icon shows the current state: the frame converges in perspective and stays parallel in orthographic.
- **Snapshot of the frame.** The "⤓ Save PNG" button in the "View" section gives you the current frame together with a caption strip: the tooth's reach, its depth below or height above the ground, the boom, stick and bucket angles, the bucket tilt and the height of axis A above the ground that all of it is measured from. A screenshot cannot do this — it drags the whole panel along and leaves the numbers tiny. On a phone the button opens the system share sheet, so the picture goes straight into the photo library or a message.
- **A colour legend** under the visibility checkboxes: tubes, plates and doublers, hydraulic cylinders, bucket, bushings and pins. The colours are not invented — they are taken from the `color(...)` calls in the model itself, and `npm test` checks that they have not drifted apart.
- **"What is welded to what"** — a checkbox that repaints the machine by RIGID BODY: the boom in one colour, the stick in another, then the bucket, the rocker, the link, the barrels and the rods, with the pins in bright red. The same colour then means "welded into one piece", a colour boundary is a joint, and a red dot is the axis it turns about. The normal palette says what a part is MADE OF; this one says WHAT MOVES relative to what — different questions, hence different modes. The colours were not picked by eye: ΔE was measured in CIE Lab on the eleven pairs that actually touch at joints, and the minimum is 30.
- **Tapping a part highlights everything welded to it** and fades the rest of the machine. "What moves together with this?" is answered in one tap, with no mode to switch. Tapping it again, or tapping empty space, clears the highlight; dragging the bucket leaves it alone.
- **An engine loading bar.** The 11 MB used to arrive in silence, which on a slow link looked like a hang. The page now fetches the file itself, as a stream, and shows "4.2 / 11 MB" — exactly once, with no double download. The tooth's depth below ground is highlighted in the HUD: it is the page's headline number.
- **Keyboard (where there is one):** `1`–`6` for the view presets, space for the dig cycle. On touch devices the handlers are not installed at all.
- **AR at full size (WebXR).** On an Android phone with Chrome (ARCore services required) a "◎ AR 1:1" button appears in the corner above the model. The machine is placed on the floor through the camera: the ring is the point on the ground under axis A (the boom foot), the axis sits at the "axis A above ground" height, and the boom points to the right, so you see the machine from the side. That is how you put it on the edge of a pit and "dig" into it; ↺ ↻ turn it about axis A. The scale is real (ARCore measures space metrically, to within a few per cent), you can walk around it, and the three sliders and "▶ cycle" move the boom, stick and bucket exactly as on screen: the same code computes the pose, OpenSCAD is not rerun. Scale 1:1 (outdoors) or 1:5 (on a table), 15° turns, "Move" puts it somewhere else. Where the browser cannot do AR (a computer; an iPhone — Safari has no WebXR for AR) there is no button. It needs https (GitHub Pages) or localhost; the address from `web/viewer-wasm.sh phone` is plain http over Wi-Fi, so before publishing, in Chrome on the phone: `chrome://flags/#unsafely-treat-insecure-origin-as-secure` → enter the address the script prints (`http://COMPUTER-ADDRESS:8767`) → Enabled → Relaunch; set it back to Default after testing. Port forwarding over a cable (`chrome://inspect` → Port forwarding) never shows the debugging permission prompt on some phones — the flag needs neither a cable nor extra software. Without a real phone only the logic can be checked: `probe.mjs --pre` with a stub `navigator.xr` (the button, the session request, the refusal message) and `__ARUI__()` — the overlay without a session.
- **AR: the room — occlusion, planes, mesh, collisions.** The session asks for three optional WebXR features. Each one is used only where the browser grants it, and a small line under the hint shows which ones it got ("depth ✓ · planes — · mesh —"). **Depth** (`depth-sensing`, Chrome on Android with ARCore Depth, which covers most current phones): real objects hide the machine, so the boom goes behind a post instead of being drawn over it. The ◐ button turns it on and off. **Planes** (`plane-detection`; in Chrome on Android behind the `chrome://flags/#webxr-incubations` flag, on Quest from the room scan) and the **room mesh** (`mesh-detection`, Quest 3; Chrome on Android does not provide it) are drawn semi-transparent: walls blue, horizontal surfaces green, objects orange. The ▦ button hides them, and collisions are still checked while they are hidden. **Collisions** are checked ten times a second. Each body of the machine contributes up to 120 of its vertices, and it counts as a collision if the segment from the body's hinge (A, B, E, cylinder pins) to a vertex crosses a wall, ceiling, table or object, or if the vertex comes within 3 cm of one. The body then turns red, red balls mark the contact points (visible even without the overlay), a "⚠ Collision: wall — boom" banner appears at the top and the phone gives a short buzz. The ⚠ button turns collision checking off (and clears the marks) when you want to see the machine pass through a wall on purpose; the room keeps being tracked, so turning it back on works at once. The floor the machine stands on is ignored, since the bucket is meant to dig below it. The vertices are a sample, so a thin object between them (a chair leg) can slip through. **Room snapshot** (`src/keep.js`). ARCore merges neighbouring planes and drops planes the camera has turned away from, which for collisions would mean the wall is gone. So a plane that disappears stays as a ghost with a dashed outline. If a live plane covers it again (the same plane, at least 60 % inside), that is a merge or a reappearance: the ghost goes, and the live plane counts one more confirmation. If nothing covers it within 5 s, a plane that has already reappeared once, or a large one (≥ 1 m²) seen for 5 s or longer, stays until the end of the session with a solid fill. Anything else is treated as noise and removed. A kept plane is dropped only if the depth map shows six times in a row (1.5 s) that the camera sees at least 25 cm further through it. Ghosts take part in the collision check. The line under the hint shows "kept N, pending M". The snapshot lives only for one session: the space of the next session starts from a different point. **Room scan** (the ▤ button, `src/scan.js`, off by default). While the button is on, the depth frames merge into one 3D model of the room. Each depth point is tied to the session space by the camera pose that ARCore tracking gives for that frame, the same tracking that stands the machine on the floor, so the planes are not needed for this. The method is the one KinectFusion uses: a sparse grid of 5 cm voxels (8×8×8 blocks created only where a surface was seen). Each voxel stores the truncated signed distance to the surface (±15 cm) and a weight. Four times a second a frame of 96 rays along its long side is added as a weighted average, so the noise of single frames averages out. Along half of the rays the space in front of the surface is cleared, so a person who walked through disappears from the model. Once a second the changed blocks are remeshed with Surface Nets. The model is split into 1.6 m chunks, and only the chunks that changed are rebuilt. It is drawn as a fill with a wireframe, coloured like the room by slope. Volume is conveyed four ways, all computed from the same distance field. Smooth normals come from its gradient, so there is no "rippling" of the faces. Ambient occlusion darkens hollows: a step along the normal that meets another surface sooner than expected means a hollow, such as the corner of a wall and the floor or under a table (about 12 cm, the field knows nothing further out). Surfaces turned sideways to the view are darker, as if a lamp were mounted on the camera. Far surfaces are slightly dimmer. The last two act only on the scan, not on the machine. The "Scan" slider in the panel sets its opacity. The range runs from barely visible to solid, and a solid model hides the camera image: you see only the model, and reality shows through only where nothing has been scanned yet. Pressing ▤ again pauses the scan, and the model stays until the session ends. The line under the hint shows "scan N k △". Memory is capped at 20,000 blocks, about 50 MB for the voxels. A room of 4 × 5 m takes about 850 blocks, so this is enough for twenty such rooms. The limit is there only so that a very long scan does not eat all the memory of the tab. The scan does not take part in collisions yet. The limits: depth is reliable only up to 4 m, and if tracking drifts the model shifts with it. On a headset without the overlay (Quest), the trigger places the machine and later puts it back into place-finding mode, and the grip button starts the dig cycle. The collision geometry lives in `src/room.js`, with no DOM, and `npm test` checks it with numbers. `__ARSCAN__(z)` scans a synthetic box room from 16 depth frames (all vertices must lie within 3 cm of its walls) and runs the snapshot for a wall at `z` (−3: kept; −2: the depth map removes it). `__ARSIM__(x)` puts the real 1:1 model in front of a wall x m away and returns the bodies that hit it (a wall at 1 m: the boom and the stick cylinder; at 6 m: nothing). Occlusion, planes and the mesh can only be checked on a real device.
- **The machine can be dragged by the bucket.** Grab the bucket body and the whole arm follows your finger: the page solves the inverse kinematics and works out the boom and stick angles. Grab the teeth and the bucket curls about its own axis while the arm stays put. Works with a mouse and with a single finger. The solution is exact and needs no iteration — joint B lies on the intersection of two circles — and `npm test` runs the forward problem through the inverse one and back (tooth error 10⁻¹² mm). An unreachable target does not freeze the arm: it follows to the edge of the working envelope, and the cylinder-stroke limit still applies. The "Lock the camera" toggle disables orbiting altogether, so you can then drag from anywhere without aiming at the bucket. On a phone it sits on the drawer handle next to the ⚠ icon — the handle is sticky and always visible, whereas the view row in the heading scrolls away. On a desktop it floats over the canvas in the bottom-left corner, next to the thing it governs. Locked, it turns orange. How to control it is written in the card behind the ⚠ icon, next to the AI warning — it lives there **permanently**, on the phone and on the desktop alike. On top of that, a first-time visitor gets the same text as a pill above the model: it stays until they have completed **two** operations (after one it is not yet clear the gesture repeats) and closes on the ×. After that the text stays behind the icon.
- **Publishing to GitHub Pages**: `.github/workflows/pages.yml` builds the page and deploys it on every push to `main` (enable it once: Settings → Pages → Source: GitHub Actions). The workflow runs `npm test` before building, so a broken model never reaches the site, and it copies `LICENSE` and `THIRD-PARTY.md` next to the page — the GPL requires this, because the page embeds OpenSCAD itself. The same links appear at the bottom of the page's panel.
- `dist/` cannot be opened by double-clicking (a page opened as a local file cannot start module workers) — you need any static web server (`npm run preview`, GitHub Pages and so on). `node_modules/` and `dist/` never reach git.
- The in-browser engine is older (2025.01) than the desktop OpenSCAD (2026.09). `npm test` checks that it builds the model without warnings, that no part comes out empty, that the JavaScript pose matches the model's echo, and that the pose block is identical in both versions of the page.

### Colours in AR

| What you see | What it means |
|---|---|
| White ring | Where the machine will stand. Shown while a place is being found; a tap places the machine there |
| Blue, see-through | A wall: a vertical plane, a wall in the room mesh, or a vertical part of the scan |
| Green, see-through | A horizontal surface: floor, table, ceiling |
| Orange, see-through | Everything else: objects in the room mesh, sloped parts of the scan |
| Dashed outline, faint fill | A plane the browser has lost. It waits up to 5 s for a decision (snapshot) |
| Dashed outline, normal fill | A lost plane kept until the end of the session |
| Fill with a wireframe (▤) | The room scan. Same colours, by slope; the "Scan" slider sets its opacity |
| Red balls, reddish body | Collision points and the part of the machine that hit something |
| Red banner at the top | The collision warning: what was hit and by which part |

## 3. A 3Dconnexion SpaceMouse in the browser

Both pages (server and WASM) can be driven with a 3D mouse without any plugin; the block of code is identical in both (`spacemouse`).

| Browser | Route | What to do |
|---|---|---|
| **Chrome / Edge / Opera** | WebHID — the page reads the mouse reports itself | "View" → the **SpaceMouse** button → in the browser dialog ("… wants to connect to a HID device") pick the mouse (or "3Dconnexion Universal Receiver") → "Connect". The dialog only appears after a click — that is a browser requirement. Permission is granted **per origin** (`127.0.0.1:8765`, `localhost:8766`, `localhost:8767` are three different ones) and lasts as long as the mouse is on and the browser is open; if the mouse reports a serial number, Chrome remembers the permission for good and the page picks the mouse up by itself (including after it is plugged back in). If not, the button has to be pressed again after a browser restart. To revoke: the icon to the left of the address → "Site settings" → HID devices. A secure context is required: https, `localhost` or a local file (verified: Chrome opens WebHID for a static `viewer.html` from disk too). |
| **Firefox** | The Gamepad API (Firefox has no WebHID) — the mouse appears as a 6-axis "gamepad" | Nothing to press: **nudge the cap or press a mouse button** while the tab has focus and the status changes to "connected (Gamepad API)". To check whether Firefox sees the mouse at all: `about:support`, or any "gamepad tester". The same route also works in Chrome as a fallback. |
| Safari | — | neither WebHID nor access to a 3D mouse through the Gamepad API |

- **Controls** ("object in hand" mode): the cap right/left and up/down pans; pushing and pulling zooms; twisting rotates about the vertical; tilting towards and away from you raises the camera. Button 1 is "Fit", button 2 steps to the next standard view. The sensitivity slider and the three inversion checkboxes (pan / zoom / rotate) are remembered in the browser. Roll (tilting sideways) is deliberately unused: the model's vertical stays vertical.
- **The bucket on the mouse (WASM page only)**: with "Lock the camera" on, the mouse no longer moves the camera but drives the **bucket**. The operator controls the bucket itself; the boom, stick and bucket work out their motion together, so the bucket travels without turning (`armFromBucket` in `src/ik.js`, an exact solution with no iteration). Push / pull moves the tooth straight forward / back, press / lift moves it down / up, tilting forward curls the bucket in (teeth up towards you) and tilting back dumps it: the bucket turns about pin E while the boom stays put. A switch under "Devices" sets the reference frame: **from the base** is an operator standing at axis A looking along the boom, so left / right, twist and roll do nothing (the swing column is not designed yet); **from the camera** lines the cap axes up with the screen, and whatever goes into the screen or sideways off the machine's plane is dropped. A cylinder reaching its end stop does not stop the bucket outright: it first keeps its angle to the stick, then slides along the stop, only horizontally or only vertically. The bucket does not jump over a point it cannot reach; it stops short of it.
- **macOS:** if the 3Dconnexion driver is installed, `3DconnexionHelper` opens the mouse exclusively (in `ioreg` the Chrome client shows `ClientSeized = Yes`), so the SpaceMouse button fails with "Failed to open the device". The fix: `tools/dev/spacemouse-driver.sh off` → press the button again → in the dialog pick **your actual mouse** (the "3Dconnexion Virtual Mouse / Virtual Data" entries are the driver's virtual devices, not it). To restore the driver for CAD applications: `tools/dev/spacemouse-driver.sh on` (it starts by itself after you log in). **Automatically:** `tools/dev/with-spacemouse.sh <command>` releases the helper before the start and restores it as soon as the command ends for any reason (Ctrl+C, closing the terminal, an error) — `tools/dev/with-spacemouse.sh web/viewer.sh`, and for the WASM page `npm run dev:sm` / `npm run preview:sm`. If the helper was not running to begin with, it is not started either. Plain `npm run dev` / `preview` leave the driver alone.
- **The 3DxWare driver** can get in the way: on Windows and macOS it sends scrolling and key presses into the browser window itself (movement appears "doubled") or holds the device. If that happens, disable the mouse for the browser in 3Dconnexion Home, or close the driver while you work with the page. For Firefox on Windows/macOS the driver usually **has to** be closed, otherwise the "gamepad" never appears.
- **Linux**: Chrome/WebHID needs access to `/dev/hidraw*` — a udev rule `SUBSYSTEM=="hidraw", ATTRS{idVendor}=="256f", MODE="0660", TAG+="uaccess"`; Firefox takes the mouse through `/dev/input/js*` with no configuration (spacenavd is not needed and must be off if it grabs the device).
- **What has been verified**: the navigation logic, automatically, in headless Chrome with mock devices of both kinds (`web/viewer-wasm/test/spacemouse.mjs`: reports 1/2/3, the 12-byte report of newer models, the buttons, the Gamepad API, the bucket with the camera locked in both reference frames). **It has never been tried with a real mouse** (there was none during development): if some axis goes the wrong way, turn on the matching inversion; if the mouse does not respond at all in Chrome, open `chrome://device-log` and see whether HID reports arrive.
- The official 3Dconnexion route (the "3DxWare for Web" SDK, a WebSocket to the driver — the way Onshape works) is not used here: it requires an installed driver and a licensed SDK, but it does work identically in every browser. If WebHID/Gamepad turn out not to be enough, that is the next option.
